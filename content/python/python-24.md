## 并发、并行、异步与竞态
**并发**表示多个任务在重叠的时间范围内推进；**并行**表示同时占用不同执行资源；**异步协作**表示任务在可等待处主动让出执行机会。

### 协程对象与执行资源

本节讨论不含 `yield` 的 `async def` 函数：调用后得到协程对象，本身不让 CPU 计算自动多核执行。若函数体含 `yield`，则定义的是异步生成器，调用得到异步迭代对象，不能与普通协程混为一类。事件循环中长时间不等待的计算会阻塞其他任务。

**竞态条件**是程序结果依赖未受控的执行交错。例如两个任务都先读计数 0，各自算出 1，最后都写回 1，实际完成两次加一却只记录一次。

### 为何一行更新仍需同步

这个三步反例说明复合读—算—写不能只因“每行代码很短”就视为不可分割。应使用合适同步或让任务返回独立结果，由单一位置汇总。

## 固定工作量下的加速比上界
设原程序耗时为 1，串行比例为 s，可并行比例为 1−s。理想 p 核且没有任何额外开销时，新耗时为 $s+(1-s)/p$，加速比
$$S(p)=\frac1{s+(1-s)/p}\le\frac1s\quad(s>0).$$
例如 s=0.2，八核的理想加速也仅为 $1/(0.2+0.8/8)=3.33$ 倍，无限核心上界为五倍。实际通信与调度只会增加成本；因此需要先估计串行部分，才能判断增加执行资源可能取得多大收益。

这里证明的是给定分解假设的成本上界，不是对所有输入规模的性能定律。

### 解释器实现的条件

常见带 GIL 的 CPython 与自由线程构建的条件不同；第三方数值库也可能释放 GIL。请以所选解释器和库的文档、代表性测量为准。[协程与任务的官方说明](https://docs.python.org/3/library/asyncio-task.html)

## 例：线程池的任务与结果
性能优化应有实际目标：输入规模多大、可接受耗时多少、内存上限多少。先用代表性数据测量，再用分析工具定位热点。把不影响总体时间的一行改快十倍，可能几乎没有收益。复杂度、数据结构和减少重复工作，通常比语法微调更值得先考虑。

```python
from concurrent.futures import ThreadPoolExecutor

def square(value):
    return value * value

values = [1, 2, 3, 4]
with ThreadPoolExecutor(max_workers=2) as pool:
    results = list(pool.map(square, values))
print(results)  # [1, 4, 9, 16]
```

这个小例子展示任务提交与结果收集接口，并不声称线程会让平方计算更快。对于极小任务，线程创建和调度开销往往超过计算时间。优化必须通过测量证明，而不是看到“多线程”三个字就判断更快。

## 线程、进程与解释器条件
并发是多个任务在时间上交错推进，并行是多个任务同时执行。大量等待磁盘、网络或其他外部响应的工作常适合线程或异步；大量纯 Python CPU 计算是否适合线程，取决于解释器构建和库实现。在常见带全局解释器锁的 CPython 环境中，线程通常不能让纯 Python 字节码获得线性多核加速；部分数值库会释放锁，新的自由线程构建也有不同条件，不能简单一概而论。

多进程可使用不同进程执行 CPU 任务，但需要进程间传输数据，启动和序列化都有成本。Windows 上多进程入口尤其应使用 __main__ 保护，避免子进程重复执行入口。共享大数组时还需考虑内存复制与通信。

## 协程调度与共享状态
async/await 适合可等待操作：任务在等待时主动让出执行机会，使其他任务继续推进。把 CPU 重计算直接放进异步函数不会自动并行，反而可能堵住事件循环。

### 异步程序还要处理失败

取消、超时、错误传播与资源释放都是异步程序的重要部分，本课只建立概念边界，不提供生产级并发框架。

共享状态会带来竞态：两个任务读到同一旧值，分别更新，可能丢失一次结果。优先让任务独立处理输入并返回结果，由单一位置合并；确实共享时再使用锁或其他同步机制。死锁、任务顺序和异常处理都要纳入设计。

## 优化顺序与性能指标
先减少无用工作，再选合适算法，然后使用成熟的向量化库，最后考虑并发与底层优化。保存基准数据、环境和正确性检查，避免一次偶然测量得出结论。性能指标应包含延迟、吞吐和内存，三者常有权衡。高级主题如分布式计算需要额外的失败模型与一致性知识。

## 任务队列、取消与资源释放
线程池的任务应有清楚输入和输出，并限制同时运行的数量。无限提交任务可能让等待队列和内存持续增长，虽然每个单独任务都很小。结果顺序、异常处理和取消行为都应在设计中说明，不能只关心成功路径。
当任务失败时，应能识别哪一份输入受到影响，并保证其他任务的资源被释放。并发程序更需要小规模验证，因为时间顺序不固定，单次成功不能证明没有竞态。
