## 快之前先确保正确
性能优化应有实际目标：输入规模多大、可接受耗时多少、内存上限多少。先用代表性数据测量，再用分析工具定位热点。把不影响总体时间的一行改快十倍，可能几乎没有收益。复杂度、数据结构和减少重复工作，通常比语法微调更值得先考虑。

```python
from concurrent.futures import ThreadPoolExecutor

def square(value):
    return value * value

values = [1, 2, 3, 4]
with ThreadPoolExecutor(max_workers=2) as pool:
    results = list(pool.map(square, values))
print(results)  # [1, 4, 9, 16]
```

这个小例子展示任务提交与结果收集接口，并不声称线程会让平方计算更快。对于极小任务，线程创建和调度开销往往超过计算时间。优化必须通过测量证明，而不是看到“多线程”三个字就判断更快。

## 并发与并行不同
并发是多个任务在时间上交错推进，并行是多个任务同时执行。大量等待磁盘、网络或其他外部响应的工作常适合线程或异步；大量纯 Python CPU 计算是否适合线程，取决于解释器构建和库实现。在常见带全局解释器锁的 CPython 环境中，线程通常不能让纯 Python 字节码获得线性多核加速；部分数值库会释放锁，新的自由线程构建也有不同条件，不能简单一概而论。

多进程可使用不同进程执行 CPU 任务，但需要进程间传输数据，启动和序列化都有成本。Windows 上多进程入口尤其应使用 __main__ 保护，避免子进程重复执行入口。共享大数组时还需考虑内存复制与通信。

## 异步是一种合作调度
async/await 适合可等待操作：任务在等待时主动让出执行机会，使其他任务继续推进。把 CPU 重计算直接放进异步函数不会自动并行，反而可能堵住事件循环。取消、超时、错误传播与资源释放都是异步程序的重要部分，本课只建立概念边界，不提供生产级并发框架。

共享状态会带来竞态：两个任务读到同一旧值，分别更新，可能丢失一次结果。优先让任务独立处理输入并返回结果，由单一位置合并；确实共享时再使用锁或其他同步机制。死锁、任务顺序和异常处理都要纳入设计。

## 可维护的优化顺序
先减少无用工作，再选合适算法，然后使用成熟的向量化库，最后考虑并发与底层优化。保存基准数据、环境和正确性检查，避免一次偶然测量得出结论。性能指标应包含延迟、吞吐和内存，三者常有权衡。高级主题如分布式计算需要额外的失败模型与一致性知识。

## 任务边界决定资源使用
线程池的任务应有清楚输入和输出，并限制同时运行的数量。无限提交任务可能让等待队列和内存持续增长，虽然每个单独任务都很小。结果顺序、异常处理和取消行为都应在设计中说明，不能只关心成功路径。
当任务失败时，应能识别哪一份输入受到影响，并保证其他任务的资源被释放。并发程序更需要小规模验证，因为时间顺序不固定，单次成功不能证明没有竞态。
